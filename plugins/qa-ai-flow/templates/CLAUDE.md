## Project Structure — Config-Driven, Not Hardcoded

**Path assumptions can go stale.** A project may start as a monorepo and get
split into separate repos later (or the reverse), for reasons outside this
flow's control (e.g. deployment/server constraints). Rather than hardcoding
one topology into this file, paths are resolved once via
`qa-ai-flow.config.json` (see "Step 0 — Resolve Project Paths" below) and
referenced everywhere else as `{backendRoot}` / `{frontendRoot}` placeholders.
See `qa-ai-flow.config.example.json` for the schema and both topology
examples below.

**Monorepo example** (`frontendRoot: "../frontend"`, `backendRoot: "../backend"`):
```
root/
├── backend/                  # {backendRoot} — Laravel
│   ├── routes/               # api.php / web.php → endpoints and pages
│   ├── app/Http/Controllers/ # request handling
│   └── app/Http/Requests/    # validation rules → validation test cases
├── frontend/                 # {frontendRoot} — Next.js or Vue.js
│   └── src/
│       ├── app/ or router/   # Next App Router pages / Vue routes → test routes
│       ├── views/            # Vue page components
│       └── components/       # UI components → use for selectors
└── qa-ai-flow/                # ← THIS TOOL
    ├── docs/
    │   └── test-cases/        # Step 1's human-readable .md output (per-page/section)
    ├── e2e/                   # generated Playwright output ({qaOutputRoot})
    │   ├── fixtures/
    │   ├── helpers/
    │   ├── pages/
    │   └── tests/
    └── CLAUDE.md              # ← THIS FILE, lives at qa-ai-flow/'s root
```

**Split-repo example** (`backendRoot: "."`, `frontendRoot: "../../my-frontend"`
— this repo IS the backend, frontend is a separate sibling repo):
```
my-admin/                    # {backendRoot} = "." — this repo IS the backend (Laravel)
├── routes/
├── app/Http/Controllers/
└── qa-ai-flow/                # this tool, nested inside the backend repo
    ├── e2e/                   # generated Playwright output ({qaOutputRoot})
    └── CLAUDE.md

my-frontend/                 # {frontendRoot} — separate sibling repo
├── src/app/ (Next) or src/router + src/views (Vue)
└── qa/                       # a DIFFERENT qa/ folder — public-site tests,
                               # not generated by this tool
```

**Two different `qa/`-style locations can coexist** — don't confuse them:
- `{frontendRoot}/qa/` (or similar) — an app-level test folder some frontend
  repos already have, testing the **public site**.
- `qa-ai-flow/e2e/` — this tool's own generated output, testing whatever
  surface `{backendRoot}`/`{frontendRoot}` point at.

If the topology changes later (e.g. repos remerge), nobody edits this file —
just update `qa-ai-flow.config.json`'s two path fields, or delete it and let
Step 0 re-detect.

## Flow Overview (Steps 1 → 2 → 3)

This repo automates the path from design/schema to running Playwright tests in
three connected steps. Each step hands off a file to the next:

| Step | Tool | Input | Output |
|---|---|---|---|
| **1 — Generate test cases** | `testcase-generator` (from any mix of a live dev/staging site, the repo, Figma screenshots and a PRD, optionally with Figma's remote MCP server — produces **frontend** TCs) | At least one of: dev/staging URL, repo path, Figma image or MCP link (+ optional PRD text) | `testcases.json` (canonical path, repo root; + `docs/test-cases/[page].md`) |
| **2 — Upload to Notion** | `${CLAUDE_PLUGIN_ROOT}/scripts/upload_testcases_to_notion.py` | `testcases.json` | Notion database pages (one per test case) |
| **3 — Automate with Playwright** | `playwright-from-testcases` (bridges to this file's Step 1–5 process below) | `testcases.json` (preferred) or `docs/test-cases/*.md` | POM + spec files in `e2e/` |

Every test case carries a `tc_id` (e.g. `TC-001`) from generation, through Notion,
into the Playwright spec's `// TC-001` comment — see the TC ID traceability rule
below.

> **Re-check mode (Step 1)** — `testcase-generator`
> also handles revising test cases after a PRD requirement or Figma design
> changes, without re-running fresh generation. Trigger it with phrasing
> like "re-check test cases for [module]" or "the Card component's states
> changed" instead of uploading a new image — no image is required for a
> re-check. It matches by module/page name, narrows by keyword, and walks
> you through a per-TC approve/reject diff before writing anything back to
> `testcases.json`. See the skill's "Re-check Mode" section for the full
> mechanics. Currently design-driven only (matches by module/page name) —
> looking a re-check up by PRD `REQ-n` isn't built yet, and re-check does
> not touch Notion or Playwright spec files (see Core Rule #7 below for why
> that's still safe).

> **Figma remote MCP server (optional, Steps 1 and 3)** — a session
> prerequisite, not an `.env` var, since MCP servers are configured via
> Claude Code's own MCP settings: connect via
> `claude plugin install figma@claude-plugins-official` or
> `claude mcp add --transport http figma https://mcp.figma.com/mcp`, then
> `/mcp` → **figma** → **Authenticate** (OAuth, browser prompt). Requires a
> Figma **Dev or Full seat** — any plan tier works, including the free
> **Starter** plan (confirmed via live testing 2026-08-05: a Full seat on
> Starter gets the same rate limit as Professional, per Figma's own MCP
> docs). Use the **remote** server, not the desktop MCP variant, which
> needs Figma's desktop app (no Linux build). The actual access gate is
> **per-file**: the file owner must share the specific file with the
> connected account and grant **Editor + Dev Mode** access — a valid
> seat alone isn't enough if the file itself hasn't been shared. If the
> connected account lacks a Dev/Full seat, or lacks access to the
> specific file being queried, the testcase-generator skill falls
> back to screenshot-only analysis with no behavior change. Step 3
> (the `playwright-from-testcases` skill) also
> uses this same connection for its Figma-mode discovery source (see that
> skill's "Frontend Discovery (Figma mode)" section) — same access gate,
> same fallback behavior when unavailable.

> Steps 2 and 3 of the Notion flow can also be run through the plugin's
> `scripts/run.py`: `python3 run.py upload ...` and
> `python3 run.py sync-results ...` — each subcommand forwards its flags to
> the underlying script. Test-case generation and Playwright automation stay
> skill-only.

## Core Rules (Always Follow)

1. **Read before writing** — always scan the frontend routes (`{frontendRoot}/src/app/` for Next.js, `{frontendRoot}/src/router/` + `src/views/` for Vue) and the backend routes (`{backendRoot}/routes/`) before generating any test file (resolved from `qa-ai-flow.config.json`; see Step 0 below). When repo access isn't available, this becomes "browse before writing" — see the `playwright-from-testcases` skill's staging discovery mode, which applies the same rule against a live staging site instead of source.
2. **Page Object Model** — every page interaction must go through a POM class in `e2e/pages/`. Never write raw `page.click()` directly inside a spec file.
3. **TypeScript only** — all files must be `.ts`. No `.js` files.
4. **No hardcoded credentials** — use environment variables from `.env.test`.
5. **Isolated test data** — use `beforeAll` / `afterAll` hooks with API helpers to seed and clean up data. Never rely on existing database state. Backend isn't always Laravel (landing pages are usually WordPress) — when it's not, or when there's no backend repo access, derive the helper from API docs/live-probing instead of the Laravel-style template (see the `playwright-from-testcases` skill's Backend Discovery section).
6. **Descriptive test names** — follow the pattern: `[role] can [action] [subject]`. Example: `"admin can publish a blog post"`.
7. **TC ID traceability** — every `test()` generated from a test case must carry a `// TC-[ID]` comment (e.g. `// TC-001`) linking back to its source test case's `tc_id`. This is how spec files stay traceable to Notion when test cases change — see the `playwright-from-testcases` skill. `tc_id`s are stable across a re-check (see Flow Overview above): a re-check revises content under the same `tc_id`, only a genuinely new state gets a new one — this is what keeps the `// TC-ID` spec comment link (and future Notion page identity) valid over time.
8. **Flag missing automation IDs — don't invent or rename them** — when a
   testable element (per `references/frontend-naming-guideline.md`'s Section 3 categories: interactive elements, validation
   elements, business entities) lacks a `data-testid`, record it as a gap
   (see the `playwright-from-testcases` skill's
   Step 3 "Missing Automation IDs" field and Step 6 report-back) rather
   than silently falling back to a text/position/xpath selector or
   inventing a `data-testid` value yourself. Never rename an existing
   `data-testid` found in source — that's the frontend developer's call,
   made only after communicating with QA (see the guideline's Section 8).

## Auth Method Detection (Read First — Before Writing Any Auth Test)

The app's authentication method is **not yet confirmed** until detected.
Before writing any auth-related test or helper, Claude Code must detect it
by reading source code (or, without repo access, by inspecting the live
login flow).

### Detection Checklist

Check in this order and stop at the first confident match. Without repo access,
inspect the live login flow instead (DevTools Network tab: which request logs
in, and does it return a token or set a cookie?).

**Step 1 — Laravel (admin panel and/or API)**
```
Read: {backendRoot}/routes/web.php, routes/api.php, config/auth.php, config/sanctum.php
Look for:
  - Sanctum: auth:sanctum middleware, /sanctum/csrf-cookie
      → SPA cookie auth (frontend on same top-level domain), or
      → personal access tokens (login endpoint returns a token, sent as Bearer)
  - Session login: Auth::attempt / Breeze / Jetstream / Fortify, Blade login form
      → admin panel logs in with a cookie session + CSRF token
  - Passport or tymon/jwt-auth: OAuth2 / JWT tokens
→ If found: auth method = the matching Laravel method above
```

**Step 2 — Next.js frontend: NextAuth**
```
Read: {frontendRoot}/src/app/api/auth/[...nextauth]/route.ts
      {frontendRoot}/src/lib/auth.ts (or authOptions.ts)
Look for: NextAuth(), providers: [], callbacks: {}
→ If found: auth method = NextAuth.js
```

**Step 3 — Vue frontend: auth store + HTTP client**
```
Read: {frontendRoot}/src/stores/ (Pinia) or src/store/ (Vuex), src/api/ or src/lib/ (axios)
      {frontendRoot}/src/router/ (navigation guards)
Look for: login action, axios interceptors, Authorization: Bearer, withCredentials: true,
          token in localStorage / cookies
→ Tells you whether it uses a Laravel token or a cookie session (Step 1)
```

**Step 4 — WordPress (landing pages)**
```
Look for: /wp-login.php, /wp-admin, a login form plugin
→ If found: auth method = WordPress cookie login (landing pages often need no
  login at all; only the admin/editor side does)
```

**Step 5 — Third-party OAuth**
```
Read: {frontendRoot}/src/app/login/page.tsx or src/views/Login.vue or similar
Look for: Google, GitHub, Auth0, Clerk, Supabase imports or SDK usage
→ If found: auth method = [provider name]
```

### After Detection — Write the Auth Helper

> ⚠️ **Unverified** — the helpers below come from general framework knowledge,
> not from a live project. Confirm the endpoint paths, field labels and button
> names against the real app before relying on them.

**If Laravel session login (Blade admin panel):**
```typescript
// e2e/helpers/auth.helper.ts
import { Page } from '@playwright/test';

export async function loginToAdmin(page: Page, email: string, password: string) {
  await page.goto('/login');
  await page.getByLabel('Email').fill(email);
  await page.getByLabel('Password').fill(password);
  await page.getByRole('button', { name: /log ?in|sign in/i }).click();
  await page.waitForURL(/dashboard|admin/);
}
```

**If Laravel token login (Sanctum personal access token / JWT):**
```typescript
// e2e/helpers/auth.helper.ts — see api.helper.ts below for getApiToken()
// Log in through the API once, then reuse the token for seeding and API tests.
```
For a **Sanctum SPA (cookie)** frontend, log in through the UI once and reuse the
session with Playwright `storageState` (see the OAuth block below for the pattern).

**If NextAuth.js:**
```typescript
// e2e/helpers/auth.helper.ts
import { Page } from '@playwright/test';

export async function loginViaNextAuth(page: Page, email: string, password: string) {
  await page.goto('/api/auth/signin');
  await page.getByLabel('Email').fill(email);
  await page.getByLabel('Password').fill(password);
  await page.getByRole('button', { name: 'Sign in' }).click();
  await page.waitForURL('/dashboard');
}
```

**If WordPress login:**
```typescript
// e2e/helpers/auth.helper.ts
import { Page } from '@playwright/test';

export async function loginToWordPress(page: Page, user: string, password: string) {
  await page.goto('/wp-login.php');
  await page.locator('#user_login').fill(user);
  await page.locator('#user_pass').fill(password);
  await page.locator('#wp-submit').click();
  await page.waitForURL(/wp-admin/);
}
```

**If OAuth (Google / GitHub / etc.):**
```typescript
// OAuth login cannot be automated via UI — use Playwright storageState instead:
// 1. Log in manually once via `npx playwright codegen`
// 2. Save auth state: await page.context().storageState({ path: '.auth/user.json' })
// 3. Reuse in tests via: use: { storageState: '.auth/user.json' }
```

> Project Overview table above (see Step 0's template-fill action), e.g.

## How to Generate Tests (Step-by-step)

When asked to write tests for a feature, follow this order:

### Step 0 — Resolve project paths, load progress, start from existing test cases, detect auth method

**Clarify stack and topology first** — ask once, then record in
`qa-ai-flow.config.json` (`stack`, `layout`): frontend (Next.js / Vue.js /
WordPress / other), backend or admin (Laravel / WordPress / other), and
whether the project is a monorepo, split repos, a single app, or has no repo
access. Don't guess these from folder names.

**Resolve `{backendRoot}` / `{frontendRoot}`:**
```
1. If qa-ai-flow.config.json exists at repo root, load it and use its
   backendRoot/frontendRoot — don't re-derive on every run.
2. Else, try heuristics:
   - Sibling ./frontend + ./backend subfolders → monorepo
   - A sibling directory one level up with a Next.js or Vue package.json → split-repo
3. If neither heuristic is confident, ask the user for frontendRoot/
   backendRoot explicitly rather than guessing.
4. Write the resolved result to qa-ai-flow.config.json for reuse next time.
```
See `qa-ai-flow.config.example.json` for the file's shape and both topology
examples.

**When repo access isn't available** (the common case for this team):
`frontendRoot`/`backendRoot` won't resolve to real directories. This isn't
a dead end — Step 3 (`playwright-from-testcases`)
will use staging-URL and API-docs-based discovery instead, resolved at that
skill's own Step 0.

**Update this file's Project Overview table (required):**
```
Once frontendRoot/backendRoot are resolved AND an auth method is detected
(see Auth Method Detection above), update the Project Overview table:
  - <YOUR_PROJECT_NAME> → actual project name (from package.json's "name"
    field at backendRoot/frontendRoot)
  - Auth Method → the detected method, e.g. "NextAuth.js"
Do this as soon as detection completes — don't leave placeholders in
place after a real run against this project.
```

**Load existing test cases and progress:**
```
Check for testcases.json (repo root) first — read it and build tests from
its test cases. Only generate test cases from scratch if no TC file is
present.

If e2e/automation-instructions/_progress.md exists, read it and

```

**Detect auth method:**
```
If not yet confirmed, run the Auth
Method Detection checklist above. Do not write any login helper or auth test
until the method is confirmed.
```

> Steps 1–3 below assume repo access (`frontendRoot`/`backendRoot` resolved
> to real directories). When it isn't available, use
> the `playwright-from-testcases` skill's staging discovery mode instead —
> same goals (routes, endpoints, selectors), different source.

### Step 1 — Map the frontend routes
```
Next.js:    Read {frontendRoot}/src/app/**/page.tsx
Vue.js:     Read {frontendRoot}/src/router/ and {frontendRoot}/src/views/**/*.vue
WordPress:  No app source to read — browse the site (staging mode) and list the pages,
            or read the theme's page templates (wp-content/themes/<theme>/page-*.php)
Goal: identify all routes and what each page renders
```

### Step 2 — Map the backend endpoints
```
Laravel:    Read {backendRoot}/routes/api.php and routes/web.php (php artisan route:list
            if you can run it), the controllers they point to, and
            app/Http/Requests/*.php for validation rules
WordPress:  Standard REST lives at /wp-json/wp/v2/; custom routes are registered with
            register_rest_route(). Form plugins (Contact Form 7, Gravity Forms) add their own.
Goal: identify REST endpoints, required auth, and validation rules
```

### Step 3 — Identify selectors
```
Next.js / Vue: Read {frontendRoot}/src/components/**/*.tsx or *.vue
Blade admin:   Read {backendRoot}/resources/views/**/*.blade.php
WordPress:     Read the theme templates (*.php) or inspect the rendered page
Goal: find data-testid, aria-labels, and role-based selectors
Prefer order: data-testid > aria-label > getByRole > getByText
```

**`data-testid` value naming** — the block above only defines which
selector *type* to prefer; it doesn't define what the `data-testid` string
itself should look like. The authoritative source for that is
`${CLAUDE_PLUGIN_ROOT}/references/frontend-naming-guideline.md` — read it
before inventing a `data-testid` value for a new component. Restated here
so this file stays actionable without always opening that doc:

- **Format:** `<page>_<element>_<component>` — lowercase `snake_case`,
  functional (describes purpose, not appearance/position/text/implementation).
  Example: `login_page_email_input`, `checkout_page_place_order_button`.
- **Dynamic/repeated elements:** `<page>_<element>_<component>_<identifier>`,
  using a stable business ID (product ID, order ID) — never a list index.
  Example: `product_list_page_product_card_12345`, not `product_card_1`.
- **Component suffix vocabulary** (non-exhaustive — see the guideline's
  Section 5 for the full table): `_input`, `_search_input`, `_button`,
  `_checkbox`, `_radio`, `_switch`, `_dropdown`, `_tab`, `_nav`, `_card`,
  `_item`, `_modal`, `_dialog`, `_error`, `_loading`.
- **If a required `data-testid` is missing** on an element that needs one
  (see the guideline's Section 3 for which elements require one): don't
  invent one and don't silently fall back to a text/xpath selector — flag
  it (see Core Rule #8 below, and
  the `playwright-from-testcases` skill's Step 3
  "Missing Automation IDs" field and Step 6 report-back).

## Page Object Model Template

// e2e/pages/ExamplePage.ts
import { Page, Locator, expect } from '@playwright/test';

export class ExamplePage {
  readonly page: Page;
  // declare locators here
  readonly submitButton: Locator;

  constructor(page: Page) {
    this.page = page;
    this.submitButton = page.getByRole('button', { name: 'Submit' });

  async goto() {
    await this.page.goto('/example');
  }

  async waitForLoad() {
    await expect(this.page).toHaveURL('/example');
  }
}

## API Helper Template (Laravel-style REST)

> ⚠️ **Unverified** — derived from general Laravel knowledge. Confirm the login
> path, response shape and resource routes against the real API (or its docs)
> and adjust. Laravel needs the `Accept: application/json` header, otherwise
> errors come back as HTML redirects instead of JSON. For a WordPress backend,
> seed through `/wp-json/wp/v2/...` using an Application Password
> (HTTP Basic auth) instead of the token flow below.

```typescript
// e2e/helpers/api.helper.ts
const BASE = process.env.API_URL ?? 'http://localhost:8000';
const LOGIN_PATH = process.env.API_LOGIN_PATH ?? '/api/login';

const jsonHeaders = {
  'Content-Type': 'application/json',
  Accept: 'application/json',
};

export async function getApiToken(): Promise<string> {
  const res = await fetch(`${BASE}${LOGIN_PATH}`, {
    method: 'POST',
    headers: jsonHeaders,
    body: JSON.stringify({
      email: process.env.ADMIN_EMAIL,
      password: process.env.ADMIN_PASSWORD,
    }),
  });
  if (!res.ok) throw new Error(`Login failed: ${res.status}`);
  const body = await res.json();
  return body.token ?? body.access_token ?? body.data?.token;
}

export async function createResource(
  token: string,
  resource: string,
  payload: object
) {
  const res = await fetch(`${BASE}/api/${resource}`, {
    method: 'POST',
    headers: { ...jsonHeaders, Authorization: `Bearer ${token}` },
    body: JSON.stringify(payload),
  });
  const body = await res.json();
  return body.data ?? body; // Laravel API Resources wrap the record in `data`
}

export async function deleteResource(
  token: string,
  resource: string,
  id: number
) {
  await fetch(`${BASE}/api/${resource}/${id}`, {
    method: 'DELETE',
    headers: { ...jsonHeaders, Authorization: `Bearer ${token}` },
  });
}
```

## Test Spec Template

```typescript
// e2e/tests/[feature].spec.ts
import { test, expect } from '@playwright/test';
import { ExamplePage } from '../pages/ExamplePage';
import { getApiToken, createResource, deleteResource } from '../helpers/api.helper';

test.describe('[Feature Name]', () => {
  let token: string;
  let createdId: number;

  test.beforeAll(async () => {
    token = await getApiToken();
    // seed data
    const entry = await createResource(token, 'posts', { title: 'Test' });
    createdId = entry.id;
  });

  test.afterAll(async () => {
    await deleteResource(token, 'posts', createdId);
  });

  test('user can [action]', async ({ page }) => {
    const examplePage = new ExamplePage(page);
    await examplePage.goto();
    await examplePage.waitForLoad();
    // assertions here
  });
});
```

## Test Coverage Checklist

When generating tests, ensure coverage for:

### Authentication
- [ ] Login with valid credentials
- [ ] Login with invalid credentials (wrong password, unknown email)
- [ ] Logout
- [ ] Access protected page when unauthenticated → redirect to login
- [ ] Access protected page when authenticated → render correctly

### CRUD Flows (per resource)
- [ ] Create — form submission, validation errors, success state
- [ ] Read — list view loads, detail view loads, empty state
- [ ] Update — edit form pre-fills, save updates correctly
- [ ] Delete — confirmation dialog, item removed from list

### API (authorization)
- [ ] Public endpoints accessible without token
- [ ] Protected endpoints return 401 without token
- [ ] Authenticated user can only access their own data
- [ ] Admin can access all data

### UI & UX
- [ ] Page loads without console errors
- [ ] Responsive layout (desktop + mobile viewport)
- [ ] Form validations show correct error messages
- [ ] Loading states and success feedback visible

## Playwright CLI Quick Reference

`e2e/` is a self-contained package with its own `package.json` and
`playwright.config.ts` (run `npm install` there once). All commands below run
from inside `e2e/`:

```bash
# Run all tests
npx playwright test

# Interactive UI mode (recommended for writing tests)
npx playwright test --ui

# List tests without running them — sanity check that specs load
# (required as part of Step 6 before reporting a module "done")
npx playwright test --list

# Record a new test by clicking through the browser
npx playwright codegen http://localhost:3000

# Run a specific file
npx playwright test tests/auth.spec.ts

# Run tests matching a keyword
npx playwright test --grep "login"

# Show HTML report
npx playwright show-report reports

# Debug a failing test
npx playwright test --debug tests/auth.spec.ts

# Run with JSON reporter, for syncing results back to Notion (see
# scripts/GET_NOTION_CREDENTIALS.md "Syncing Results Back")
npx playwright test --reporter=json > playwright-report/results.json
```

## What Claude Code Should NOT Do

- ❌ Do not write test logic directly in spec files — always use POM
- ❌ Do not hardcode URLs, emails, or passwords — use `.env.test`
- ❌ Do not assume database state — always seed via API in `beforeAll`
- ❌ Do not use `page.waitForTimeout()` — use `expect().toBeVisible()` or proper awaits
- ❌ Do not create `.js` files — TypeScript only
- ❌ Do not skip `afterAll` cleanup — always delete seeded data after tests
- ❌ Do not invent or rename `data-testid` values — flag missing ones
  instead (see Core Rule #8 and `references/frontend-naming-guideline.md`)
